# Wallet authentication

Part of #969. The canonical server verifier is `site/api/_wallet-proof.js`.
All wallet-dependent endpoints must use it, directly or through `_data-auth.js`.

## Verified identity boundary

The current Dapper login owner stores the proof's own account address as both
the linked wallet and signing address. Server authorization requires those
addresses to match after normalization. Client headers cannot establish a
relationship between different wallets. Any future linked-account support must
verify that relationship server-side before it can grant access.

Account proofs are verified against the authorized wallet and the canonical
application identifier. Their nonce must match the 32-byte hexadecimal envelope
generated by the current login owner. FCL verifies their keys against the explicit
account address; individual account-proof signatures need not repeat that address.
User-message signatures must all identify the authorized wallet, including when
multiple account keys are used. The installed FCL implementation derives the
user-message verification address from the first signature.

Only a literal `true` from the selected FCL verifier grants access. A false result,
unexpected result, unavailable SDK, or thrown verification error denies access.
There is no caller option to accept a proof after a verification error.

`site/validate-wallet-proof.mjs` executes the verifier with a mocked SDK and the
actual data-auth/opt-in consumers without network calls or database writes.
It runs in the API/persistence validation domain.

## Remaining session work

This first PR fixes identity binding and fail-open verification. It does not add
proof expiry or replay protection: the current account-proof nonce is generated
in the browser and signed-message proofs use a static message. Server-issued,
expiring challenges and replay-safe session establishment remain the next
authentication step in #969. Do not describe the existing nonce-format check as
proof freshness or replay prevention.

Manual testing should cover fresh Dapper opt-in, restoring an existing valid
session, private preferences/watchlists/evaluations, and opting out and back in.
Persisted sessions whose claimed wallet differs from their proof must be linked
again with the correct account; they must not receive a compatibility bypass.
